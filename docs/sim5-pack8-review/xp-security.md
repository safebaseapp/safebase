# XP security audit — code and local database only

No production database access, migration, profile edits, XP writes or paid Supabase projects/branches were performed. Production does not yet have `sim5_runs` / `sim5_xp_best`; there is no staging instance. LIVE SUPABASE: NOT TESTED. Full-mode persistence cannot be considered release-verified until an approved migration and staging end-to-end test exist.

The trusted API checks the authenticated server identity and active entitlement before start/read/save. The save handler replays the six-finding event log, derives the score and report, verifies ownership/revision/log-prefix and calls service-role-only `save_sim5_run`. Client-provided XP, score, identity and entitlement do not determine the award. DEMO does not instantiate persistence; browser tests check no writes and empty guest localStorage.

The SQL transaction locks the run, checks compare-and-swap revision, and serializes each user's best-award updates with an advisory lock. Replaying is unlimited; the static mission awards only improvement to the lifetime best score ×2, at most 200 XP. Duplicate retries return the existing result. History reads are owner-only under RLS; authenticated/anonymous roles cannot insert/update/delete runs, XP-best, legacy attempts or progress, or call the award RPC. Existing service-role Labs writers retain access. No existing history is rewritten. Levels use the existing Labs curve; prior totals and streaks are preserved and incremented only on eligible awards.

Audit change: SQL three-valued NULL comparisons could let a malformed trusted caller omit report fields/revision. The server replay already rejected these, and clients could not call the RPC. The migration now rejects NULL inputs/missing schema/score/phase/completed array, and requires exactly the six distinct mission IDs. This is defense in depth, not a new client authorization path.

Local PostgreSQL 17, disposable Docker container with `--network none`: **20 checks pass**, including migration against existing Labs schema, authenticated/anon role boundaries, owner isolation, malformed reports, duplicate retries, parallel runs, parallel identical submissions, partial/finalized runs, preserved totals/streak/level and existing service writer/attempts. Supabase auth roles are fixtures, not live auth.

Migration required after separate approval: `app/supabase/migrations/20261020_sim5_runs.sql`, depending on the existing Labs schema (`20260930_sernem_labs_v1.sql`). Review deployment order against the actual migration ledger; do not rerun an already applied Labs migration. The SIM migration intentionally revokes legacy direct-client writes to `lab_user_progress` / `lab_attempts`; inventory any external writers before production approval. Server environment must provide the configured Supabase public credentials and service-role key. None were requested or configured in this cloud task.
